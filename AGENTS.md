# Правила работы с кодом

## Главный принцип

Сначала сохраняй границы FSD, затем выбирай самое прямое решение внутри них. Простоту оценивай по объёму контекста, который нужен для понимания изменения. Дополнительная абстракция полезна, когда уменьшает этот объём, а не скрывает зависимости за ещё одним переходом.

## Границы FSD

Порядок слоёв: `app → pages → widgets → features → entities → shared`. Между слоями зависимости направлены только вниз; промежуточные слои можно пропускать. Создавай только нужные слои и сегменты. `processes` и собственные слои не добавляй.

Слайсы одного слоя изолированы друг от друга. Это относится и к типам, динамическим импортам, реэкспортам и зависимостям в стилях. В `app` и `shared` слайсов нет: они состоят из сегментов, которые могут зависеть друг от друга внутри своего слоя.

Связь между независимыми слайсами собирай на ближайшем подходящем слое выше через их публичные контракты. Если слайсы постоянно требуют знания внутренностей друг друга, пересмотри их границы. Не маскируй такую связь общим хранилищем, шиной событий или посредником в нижнем слое. Группа слайсов в общей папке не получает собственного общего кода или публичного API.

Исключение для связей между сущностями — адресный API `@x`. Если модель одной сущности действительно включает другую и связь нельзя разумно убрать, `entities/order` может обращаться к `entities/product/@x/order`. Этот API экспортирует только необходимое для указанного потребителя. Используй его только в `entities`, без циклических зависимостей; логику совместного пользовательского сценария размещай выше.

## Размещение кода

Код, нужный одной странице, по умолчанию оставляй в её слайсе: UI, состояние, запросы и логику сценария. Выделяй `feature` вокруг самостоятельного пользовательского действия, `widget` — вокруг крупного самостоятельного блока интерфейса. Повторное использование — основание для выделения; для виджета им также может быть независимый блок сложной страницы. Само появление компонента или запроса не требует нового слайса.

В `entities` размещай модели и поведение предметных сущностей, общие для разных сценариев. Отдельный ответ API не обязывает создавать сущность. В `shared` держи инфраструктуру и код без бизнес-правил приложения. Несколько потребителей не делают предметный код частью `shared`; не переноси туда модели и типы ради обхода границ.

Сегменты называй по назначению, например: `ui`, `api`, `model`, `lib`, `config`. Типы, состояние и запросы распределяй по их владельцам, а не собирай в общие каталоги `types`, `store` или `services` вне FSD. Если объединение похожего кода требует флагов для разных сценариев и связывает их изменения, оставь реализации раздельными.

## Модули и типы

Публичная граница — слайс, а в `app` и `shared` — сегмент. В `shared/ui` и `shared/lib` используй отдельные входы независимых компонентов и библиотек, например `shared/ui/button/index.ts`. Это модули внутри сегментов, а не дополнительные слайсы. Внутренним папкам слайса не нужны собственные индексы только из-за наличия папки.

- Корневой `index.ts` модуля содержит явные реэкспорты публичного API и импорты собственных стилей. Реализацию держи в других файлах. Экспортируй только необходимое потребителям; `export *` не используй.
- Между модулями импортируй значения и типы через их публичные входы. Для слайса это корневой `index.ts`, кроме описанного адресного API `@x`. Индекс вложенной папки не открывает доступ к внутренностям чужого слайса. Индексы для реэкспорта всего слоя не создавай.
- Внутри модуля используй прямые относительные импорты из файлов, без обращения к собственному `index.ts`.
- Объявления `type` и `interface` держи в `types.ts` или `*.types.ts` в соответствующем сегменте рядом с кодом, которому они принадлежат. Для импорта и реэкспорта типов используй `import type` и `export type`.

## Стили

Стили храни в файлах своего модуля; у слайса — в `ui`. Подключай их из `index.ts` модуля, чтобы потребитель получал UI вместе с его оформлением без отдельного импорта CSS. Глобальные стили приложения подключай из `app/styles/index.ts`, общие токены оформления держи в `shared`.

Стили модуля должны действовать в его границах. Внешний код не должен зависеть от его внутренних классов, DOM-структуры или порядка подключения чужих стилей. Варианты оформления задавай через публичный контракт модуля; расположение модулей относительно друг друга определяй на уровне их композиции.
